# Contract v7.4 integration

Prepared from the operator's `Obsidian-v7.4-all-contracts.zip` and `v7.4-dapp.md`.
The archive is preserved unchanged under `contracts/source/v7.4/`, including its
OpenZeppelin dependencies. The application has no new brand name.

This branch combines main's existing VPN fixes with the previous experience upgrade.
It does not deploy Solidity, migrate funds, fulfill VPN orders, or submit transactions.

## Activation is pending the operator's addresses

`NEXT_PUBLIC_FACTORY_ADDRESS_V7_4` is deliberately blank. The factory address in the
supplied documents is a reference, not an activated default. Legacy
`NEXT_PUBLIC_FACTORY_ADDRESS`, fixed round/weekly window variables and old window
localStorage keys are no longer used. The known retired v7.1 factory is rejected.
Missing/invalid configuration disables writes and presents a configuration notice.

After the operator supplies the factory, put it in `.env.local` under the new key,
keep the real WalletConnect project ID, confirm `NEXT_PUBLIC_CHAIN_ID`, then rebuild.
Both windows are resolved live on that chain with `getLatestWindow()` and
`weeklyWindow()`. A supplied current window can be compared with discovery, but must
not be pinned: rounds rotate every twelve hours. Before signing a write or token
approval, the app reads the latest window again. A rollover requires refreshing the
payment/allowance instead of using a cached spender. Contract writes are simulated
before asking the wallet to send them.

## Behavior

- $55 payoff only for entrance 50 with positive debt. Price is fixed even for
  partially repaid debt. Debt clears; earnable resets to $350, not an addition.
- $110 upgrade keeps debt and resets earnable to $1,050 for indebted accounts.
  An indebted entrance-100 account cannot use the $55 payoff.
- Only entrance 100 renews, below its earnable cap and with fewer than two renewals
  since its last flash. These rules apply at every stage.
- Direct bonuses pay in full; binary payouts repay debt; weekly points remain zero
  while debt exists. Disclosures appear on entry, top-up and user screens.
- History bounds use factory `roundCounter()`, including round zero. User history
  sends the older offset first and newer offset second, as the Solidity requires.
  Chart labels show actual round numbers; streaks count from newest backwards.
- `getUserBulkInfo`'s second field is unmatched volume, not total entry volume.
- No invented stage-4 launch fallback. Existing weekly pool views remain on the
  live weekly window; this UI has no custom roundsLeft workaround.

## Source versus prose

The ZIP is authoritative for ABI generation. The dapp-facing wallet change method
is `resetWalletAddress(address)` on SmartContractWindow. It calls the factory's
`changeWalletAddress(msg.sender, newAddr)` internally; the latter is not a user
window method. `_userTopupsSinceFlash(uint48)` returns uint256. Generated ABIs
include the new events, plus factory errors that can bubble through window calls.
Existing explorer activity remains supported; a full event indexer is not added.

## Verification

Run `node scripts/tests/contract-v74.cjs`, `node scripts/tests/chunk-recovery.cjs`,
`npx tsc --noEmit`, and `npm run build` with your existing WalletConnect ID.
The regression tests exercise eligibility, partial debt, renewal boundaries,
round-zero history, actual hook calldata, wrong-chain/missing-config protection,
window rollover, failed simulation and a mocked successful write. No real funds
are used. Live deployed reads and wallet flows remain pending address activation.

ABI regeneration needs solc 0.8.36 available to Node (for example via a separate
npm prefix and NODE_PATH). Run `node scripts/generate-v74-abi.cjs`. Compiler settings
match the archive: optimizer 500 runs, viaIR, London. Generation requests ABI only;
it is not a contract bytecode audit or deployment verification.
